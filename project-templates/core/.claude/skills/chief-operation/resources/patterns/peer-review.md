# Peer Review - ピアレビュー運用

## 概要

V2.1で導入されたメイド間ピアレビューの運用方法。
メイド長の負荷を軽減し、レビュー処理を効率化する。

## ピアレビューフロー

```
┌─────────────────────────────────────────────────────────────┐
│  ピアレビューフロー                                          │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  【Phase完了時】                                             │
│      │                                                       │
│      ├── 自動承認条件を満たす → 自動承認                    │
│      │                                                       │
│      ├── 軽微な変更 → ピアレビュー（他メイドが担当）        │
│      │   └── メイド長の負荷軽減                             │
│      │                                                       │
│      └── 重要な変更 → メイド長レビュー                      │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

## ピアレビュー委任基準

### 委任可能なケース

| 基準 | 閾値 | 備考 |
|------|------|------|
| 変更行数 | <= 100行 | 軽微な変更 |
| タスク種別 | Action | Phase/Goal は委任しない |
| セキュリティ変更 | なし | .env, credentials 等 |
| 設定ファイル変更 | なし | config.*, *.yaml 等 |
| 担当メイドの専門外 | 他メイドが得意な領域 | 相互補完 |

### 委任不可なケース

| 基準 | 理由 |
|------|------|
| Phase/Goal 成果物 | 重要な判断が必要 |
| セキュリティ関連変更 | メイド長確認必須 |
| 設定ファイル変更 | 影響範囲が広い |
| アーキテクチャ変更 | 設計判断が必要 |
| 差し戻し後の再提出 | 指摘対応の確認が必要 |

## 手順

### Step 1: 委任判断

```bash
# レビュー待ちタスク確認
maidctl review list

# タスク詳細確認
maidctl task get TASK_ID
# → 変更行数、ファイル種類を確認
```

**判断フロー:**
```
変更行数 <= 100 ?
    │
    ├── Yes → セキュリティ/設定変更なし ?
    │           │
    │           ├── Yes → ピアレビュー可
    │           │
    │           └── No → メイド長レビュー
    │
    └── No → メイド長レビュー
```

### Step 2: レビュアー選定

**選定基準:**
| 優先度 | 基準 | 理由 |
|--------|------|------|
| 1 | 関連領域の得意なメイド | 品質向上 |
| 2 | 現在タスクが少ないメイド | 負荷分散 |
| 3 | 実装者と異なるメイド | 客観的視点 |

**メイド得意分野（参考）:**
| メイド | 得意分野 |
|--------|----------|
| emma | コードレビュー |
| sophia | ドキュメント |
| lily | テスト |
| rose | リファクタリング |
| alice | 調査・分析 |
| may | バグ修正 |
| flora | 新機能実装 |
| luna | 設定・環境構築 |

### Step 3: レビュー依頼

```bash
# レビュー担当メイドに通知
maidctl notify {レビュー担当メイド} "#TASK_ID のコードレビューをお願いします。変更内容: [概要]。reports/current_{実装者}.md を参照してください。"
```

### Step 4: レビュー結果の収集

ピアレビュー担当メイドが完了報告したら:

```bash
# レビュー結果を確認
# reports/current_{レビュー担当メイド}.md

# 承認の場合
maidctl task update TASK_ID --review-status approved

# 差し戻しの場合
# → 修正サブタスク作成（review-queue-management パターン参照）
```

## レビュアーメイドの作業

レビュー担当メイドは以下を実施:

### 1. レビュー開始

```bash
# 自分のタスクとしてレビューを受け取る
maidctl my-task

# ステータス更新
maidctl my-status working
```

### 2. レビュー実施

確認観点:
- コード品質（可読性、命名規則）
- ロジックの正確性
- テストの妥当性
- ドキュメント整合性

### 3. レビュー報告

```bash
# 報告書にレビュー結果を記載
# reports/current_{自分}.md

# ステータス更新
maidctl my-status completed

# メイド長に報告
maidctl notify chief "#TASK_ID のピアレビュー完了しました。[結果: 承認/要修正]"
```

## 判断ポイント

| 状況 | 判断 | アクション |
|------|------|-----------|
| 軽微な変更 + 空きメイドあり | ピアレビュー委任 | メイドに依頼 |
| 軽微な変更 + 全メイド稼働中 | メイド長レビュー | 自分で実施 |
| 重要な変更 | メイド長レビュー | 自分で実施 |
| 専門領域外 | ピアレビュー委任 | 得意なメイドに依頼 |

## 注意点

- 【重要】Phase/Goal のレビューは委任しない
- 【禁止】セキュリティ関連のピアレビュー委任
- 【推奨】レビュアーは実装者と別のメイドを選ぶ
- 【推奨】負荷分散を考慮してレビュアーを選定

## 事例

### 事例1: 軽微なバグ修正 → ピアレビュー

**状況**: may が10行のバグ修正を完了
**判断**: 軽微な変更、emma が空いている
**対応**:
```bash
maidctl notify emma "#123 のコードレビューをお願いします。10行のバグ修正です。"
```

### 事例2: 設定ファイル変更 → メイド長レビュー

**状況**: luna が config.yaml を変更
**判断**: 設定ファイル変更 → 委任不可
**対応**: メイド長が自分でレビュー

### 事例3: UI実装 → 専門メイドにピアレビュー

**状況**: alice が UI コンポーネントを実装
**判断**: flora が UI 実装に詳しい
**対応**:
```bash
maidctl notify flora "#456 の UI 実装レビューをお願いします。React コンポーネントです。"
```
