# パターンファイル テンプレート

## 概要

`resources/patterns/` に配置するパターンファイルのテンプレート。
スキルの具体的な運用手順、ワークフロー、診断パターンを記述する。

---

## テンプレート（基本形）

```markdown
# {パターン名} - {日本語名}

## 概要

{このパターンの目的を1-2文で説明}

## 適用条件

- {条件1}
- {条件2}
- {条件3}

## 手順

### Step 1: {ステップ名}

{具体的な手順}

### Step 2: {ステップ名}

{具体的な手順}

## 注意点

- {守るべきルール1}
- {守るべきルール2}

## 事例

### 事例1: {事例タイトル}

**状況**: {どういう状況だったか}

**対応**: {どう対応したか}

**結果**: {どうなったか}
```

{詳細}

## 各セクションの書き方

### 概要

- **1-2文で完結**
- パターンの目的を明確に
- 「〜する手順」「〜のテンプレート」のように具体的に

```markdown
# 良い例
タスク完了時に作成する報告書のテンプレートと記載ルール。

# 悪い例
報告書について説明します。
```

### 適用条件

- **箇条書き3-5項目**
- 具体的なトリガー状況を列挙
- 曖昧な表現を避ける

```markdown
# 良い例
## 適用条件
- タスク完了時の報告書作成
- ブロック時の状況報告
- エスカレーション時の詳細記載

# 悪い例
## 適用条件
- 報告が必要な時
```

### 手順/ステップ

- **Step N 形式で番号付け**
- 各ステップは1つのアクションに集中
- コマンドやコード例を含める

```markdown
# 良い例
### Step 1: ステータスの確認

{コマンド}

pm2 status

確認項目:
- status: online/errored/stopped
- restarts: 再起動回数

# 悪い例
### Step 1

まずステータスを確認します。pm2 status を実行して、その後いろいろ確認します。
```

### 注意点

- **箇条書きで簡潔に**
- MUST/SHOULD/MUST NOT を明示
- 理由も添える

```markdown
# 良い例
## 注意点
- **専用ファイル原則**: 自分の報告ファイルのみ更新
- **タイムスタンプ**: 必ず `date -Iseconds` で取得（推測禁止）
```

### 事例

- **実際に起きたケースを記載**
- 状況 → 対応 → 結果の流れ
- コード/ログの引用があると良い

```markdown
# 良い例
### 事例: MCPサーバー頻繁再起動（#114）

**症状**: PC再起動以降、エージェント未使用状態で3回再起動

**調査結果**:
1. 直接原因: PM2のメモリ制限（200MB）超過
2. 根本原因: transport.onclose の無限再帰

**修正**: transport.onclose = null で循環を断ち切り
```

## サイズガイドライン

| パターン種別 | 推奨行数 | 例 |
|-------------|---------|-----|
| シンプルなワークフロー | 50-80行 | task-workflow |
| テンプレート提供型 | 80-130行 | report-format |
| 診断パターン | 150-220行 | mcp-server |
| レビュー観点型 | 100-150行 | common |

**200行を超える場合**: 先頭に目次を追加

```markdown
# {パターン名}

## 目次

- [概要](#概要)
- [適用条件](#適用条件)
- [診断手順](#診断手順)
- [一般的な問題と解決策](#一般的な問題と解決策)
- [事例](#事例)

## 概要
...
```

## チェックリスト

パターンファイル作成後に確認:

- [ ] 概要が1-2文で完結しているか
- [ ] 適用条件が具体的に列挙されているか
- [ ] 手順が Step N 形式で番号付けされているか
- [ ] 注意点が明記されているか
- [ ] 事例が含まれているか
- [ ] 200行以下か（超える場合は目次追加）
- [ ] ファイル名が内容を表しているか
